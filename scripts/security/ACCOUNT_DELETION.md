# Self-service account deletion

The native confirmation deletes the verified user's login identity and public profile, not a caller-selected account or a shared application. The server requires same-origin mutation checks, a fresh Auth identity, the captured account header, and an unguessable deletion-intent UUID. An account with an enrolled verified authenticator must step up before deleting. The runtime mutation limiter remains enforced. Administrator eligibility and membership are independent of the right to delete an ordinary own account; the final eligible administrator cannot self-delete while no other eligible administrator remains.

`prepare_profile_deletion` is service-only. It takes the existing Auth-parent/719/730 locks, plus the shared administrator-membership lock, before recording a durable deletion fence. Owned assets outside `avatars` and `portfolio-assets`, contradictory ownership, or another account's UUID namespace block the request before its fence or any media is changed. Such cases need a separately reviewed preservation decision, not automatic deletion or reassignment of shared RazinFlix assets.

The manifest derives targets from actual Storage ownership, the private media registry and the exact verified-account namespace in the two profile buckets. It never derives deletion targets from public image URLs or a request's file names. It returns at most 200 exact destinations at a time. The server removes batches through the supported Storage API, then re-reads the manifest; it does not edit `storage.objects`, its ownership or its underlying catalog rows. Non-UUID-prefixed legacy objects require actual owner proof. Other users and shared app records remain untouched.

The fence rejects profile provisioning, transactional profile/payment edits, media reservations and media registration for that identity. Existing media reservations keep deletion busy before any byte removal. A dropped upload/registration response retains the 120-second reservation rather than claiming rollback. The 120-second window exceeds the upload route's 30-second runtime and five-second dependency deadline; the design assumes the bounded runtime and provider request complete within that conservative window. A provider-side operation that continues beyond this window is an infrastructure incident requiring inventory reconciliation, not an absolute physical-erasure guarantee.

Once the manifest is empty and no reservation is live, the server calls `auth.admin.deleteUser(id, false)` and verifies authoritative Auth absence. Auth's supported hard deletion removes refresh sessions and cascades only the owner's relational rows, journal, permissions and registry. An Auth deletion trigger removes that owner's FK-less obsolete `user_links` and `user_contacts`, and anonymizes only the deleted UUID's roles in permission-audit records while preserving other participants' records. Obsolete tables have no browser write grants, so an unexpired old access token cannot recreate them. Existing public views/ownership rules are not relaxed.

Partial byte removal or an upstream failure is explicitly uncertain: some images may already be removed. The fence remains so the same owner can retry safely without new content being published mid-deletion. A busy intent is already started; dismissing its dialog does not undo it. A new nonce from the same verified account can resume an intent. Completed technical receipts retain only an operation UUID, a server HMAC, timestamps and completion status, not email, profile content or the raw Auth UUID. They survive the Auth cascade and permit the original request to reconcile a lost response. An unauthenticated status retry can only inspect an existing matching receipt and finish its bookkeeping after verified Auth absence; it cannot start a deletion or choose new targets.

Clearing the browser's own account and navigating home happens only after a matching account/operation receipt. Another identity signing in during a request must not have its cookies or local session cleared by a late response. Existing access JWTs remain cryptographically valid until expiry, but parent checks and revoked obsolete write grants prevent profile resurrection; Auth hard deletion prevents new refresh sessions.

## Release and verification

Apply the additive forward migration before deploying its compatible callers. The guarded bootstrap contains the identical contract for an empty isolated project only. Release in two phases: first deploy the reserved-media handlers with `NSSO_ACCOUNT_DELETION_ENABLED=false` and `NEXT_PUBLIC_ACCOUNT_DELETION_ENABLED=false`; prove the exact custom-domain cutover and wait at least 120 seconds, exceeding the old upload runtime. Then deploy the same reviewed revision with both flags `true`. The DELETE endpoint defaults closed unless the private server flag is explicitly `true`. Verify that superseded immutable deployment URLs require Vercel authentication and that no public custom domain still serves an unsafe older handler. Do not enable deletion if that protection or drain cannot be demonstrated. Never run the synthetic proofs against production or test by modifying a customer's account.

`account-deletion-proof.mjs`, invoked by the required fresh-project gate, creates and removes only local synthetic Auth accounts, profile children and Storage objects. It exercises real legacy-owned non-prefix files, service-owned registry files and orphans, a finishing upload lease, stale writes, alias receipts, operation/deletion concurrency, eligible-administrator concurrency, and preservation of another account and shared RazinFlix film/poster. Unit tests additionally cover transport failures and exact account/nonce checks; rendered browser fixtures cover confirmation, cancellation and account changes.

Deletion removes active application rows and owned profile bytes. Provider backups, encrypted owner-held recovery snapshots, security log retention, browser caches and third-party payment-provider records have their own retention and are not erased by this feature. Historical snapshots must be handled under the existing restricted recovery-retention policy; do not restore deleted accounts or old credentials from them. Technical receipt retention must preserve replay/status consistency until a separately reviewed retention change is approved.
