# Validated profile media

The three profile upload clients use `uploadProfileMedia` and the authenticated `/api/profile/media` endpoint. `X-Nsso-Account` must match a freshly verified Auth identity before body work, so an old account's crop cannot be uploaded into a newly signed-in account. It is a precondition; the header never chooses the upload owner. Origin checks and both IP/account upload quotas precede decoding.

The endpoint reads a bounded multipart body and accepts one file plus `avatar`, `project`, or `product`. Avatar input is limited to 5 MiB; portfolio input to 10 MiB. Both declared MIME and raster signatures must agree. Sharp then actually decodes a still JPEG/PNG/WebP/GIF/AVIF, limits decoded images to 20 million pixels, rotates and re-encodes a metadata-free JPEG with a five-second processing limit. Output is capped at 5 MiB and resized within 2048 pixels for avatars or 4096 for portfolio media. Original filenames, EXIF, active payloads and appended bytes are not preserved.

Storage receives a new `${verifiedUserId}/${kind}/${randomUUID}.jpg` with `upsert:false`. The service role may create an ownerless Storage catalog row, so the service-only `register_profile_media` RPC validates the actual stored MIME/size and records ownership in `private.media_assets`. Browser clients cannot write that registry. There are no direct SQL writes to Storage catalog ownership.

Registration uses the same bucket/path on retry. If both replies are unavailable, the endpoint keeps the object and returns a safe failure: an earlier RPC might have committed, so deleting the object would be unsafe. Such an unlinked upload may require later inventory/reconciliation; no unconfirmed public URL is returned. Existing image URLs are never overwritten or deleted by this flow. Crop state remains available when upload or the later versioned profile/product update fails.

Deploy the additive registry/RPC before this source. Verify current clients use the validated endpoint, then apply the separately reviewed authenticated Storage INSERT/UPDATE cutover. Until that final database grant cutover, direct authenticated Storage clients can still bypass application decoding; bucket MIME/size checks alone are not byte validation. The cutover must preserve public reads and legacy object URLs. Do not claim the bypass is closed from source deployment alone.

Handler tests use real Sharp decoding and mocked Auth/Storage to verify actor/origin/account/quota ordering, fake JPEG/SVG/MIME denial, foreign path rejection, streamed body/input/pixel bounds, metadata removal, fresh object identities, and uncertain-registration behavior. Database/Storage HTTP rehearsal separately verifies registry ACLs, ownership mapping and the staged direct-write cutover.

`rehearse-profile-media.mjs` is an opt-in local proof using synthetic Auth actors, real Sharp JPEG bytes, the actual Storage API and PostgREST RPC. It verifies all three canonical kinds, ownership mapping to the real ownerless Storage object, byte round trips, idempotent registration, inconsistent actor/path/bucket/metadata denials, and anonymous/authenticated registry denials. It never edits Storage catalog rows or accepts a remote stack; cleanup uses Storage and Auth APIs.
